## Problem Statement

cs-agent runs the same resolve/escalate pipeline through three surfaces —
CLI, MCP server, DevUI workflow. The approved plan-of-record post-publish
order (design-2026-09-05.md "Distribution Plan") names the HTTP API
(`POST /ask`) as the next item after URL crawl (shipped in v0.1.1, PR #5).
This cycle: the retrieval dedup fix (issue #6) was explicitly deferred to
keep it open as a documented limitation, and the effort goes to the HTTP
API instead.

## What Makes This Cool

The semantic inversion: **escalate is a domain outcome (200), not an HTTP
error.** Every other LLM API streams confident-sounding tokens; this one
returns a gated, complete answer where a refusal is a first-class result
with missing citations. Consumers branch on `resolved:false` + non-null
`missing[]` — the canonical `AskResult` fields, unchanged — and only
infrastructure failures are errors at all.

## Constraints

- Verifier = ONE model call; worst case 3 LLM calls per ask. No new LLM call.
- Verdict before output: nothing returns until resolve/escalate exists. No streaming in v1 — this applies to HTTP too.
- Escalate is the safe default; never fabricate a verdict (a proxy timeout surfaces as an error, never an escalated answer).
- One result object, now four surfaces: `answer · citations · claims[] · calls · seconds · estimated_cost` — HTTP serializes it, never re-builds it.
- Validate loudly: named structured errors, no stack traces.
- Env vars only, no config files. No auth, no rate limiting, no request logging in v1.
- Weekend-budget v1; issue #6 stays deferred (documented limitation).

## Premises (all agreed in session, 2026-09-07)

1. **Escalate is a 200.** POST /ask returns the canonical `AskResult` JSON
   (question, resolved, answer, missing, claims, citations, calls, seconds,
   estimated_cost) verbatim. `resolved:false` with `answer:null` and
   `missing[]` populated — the escalate outcome — is a valid answer, NOT a
   5xx. No `verdict` field is invented; the HTTP layer does not reshape the
   result object. Only infra failures (bad env var, corrupt store, empty
   store, model transport) map to 5xx named structured errors.
2. **Sync only, no streaming, no async jobs.** The response is one complete
   result. Timeout mechanism, decided: **v1 imposes NO server-side ask
   timeout** — the pipeline runs to completion. v1 is non-cancellable
   mid-run: `AskPipeline.Run` is synchronous with no `CancellationToken`,
   and threading one through Core would break "zero new logic" (deferred
   with the async upgrade). A client disconnect is observed only AFTER
   completion, to skip writing the response — the model spend is lost;
   that is the accepted sync-only cost. A 504 can only originate from a
   reverse proxy in front of the server (the Docker-era deployment); the
   API itself never fabricates a verdict and never emits 504.
   Second-opinion challenge on slow-day p95 was resolved as: keep sync,
   MEASURE p95 from the live eval (`seconds` field already exists per
   ask); if p95 > ~15s, the 202 + GET /result/{id} upgrade is
   pre-authorized as the named follow-up.
3. **Fourth surface, zero new logic.** HTTP layer is serialization + error
   mapping only; pipeline logic, MCP, DevUI untouched. The ONE CLI touch:
   `ask --json`'s serializer line refactors onto the shared Core instance
   (byte-identical output), and eval's `JsonOpts.Indented` consolidates
   onto the same instance — three consumers, one declaration (eng-review
   D6/D13; outside voice #10).
4. **GET /health is liveness-only.** No model call, no store probe. It
   answers "is the process up", not "will the next ask work".
5. **Delivery is a new `cs-agent serve` CLI subcommand (Kestrel).** Port via
   env var or flag; env-vars-only rule intact; no auth in v1.

## Approaches Considered

### Approach A: serve in CLI (minimal viable)
Routes live directly in the CLI project's Program alongside existing
subcommands; hand-rolled DTO validation, switch-based error→status mapping.
Fastest ship (CC ~1.5h), but HTTP contract logic grows inside the CLI host
and Docker later packages the CLI process rather than a clean server
library. Ruled out: scatters HTTP concerns into the CLI host permanently.

### Approach B: dedicated CsAgent.Http library project (chosen)
Endpoints as extension methods, typed error-name→ProblemDetails mapping
table (`urn:cs-agent:<component>:<name>`), auto OpenAPI,
`WebApplicationFactory` tests plus one JSON-identical contract test vs
`cs-agent ask --json` (fake-model seam, `seconds` masked). The CLI's
`serve` subcommand just calls the library.

### Approach C: evidence flag (lateral, declined)
`?evidence=true` on POST /ask returning the trace bundle (retrieved chunks,
raw verifier claims JSON, per-claim support) in the same sync response.
Strongest portfolio demo — "escalations auditable over curl" — but
re-opens the scope call declined in this session (plan-faithful shape) and
exposes rejected-draft content that must be clearly labeled gated. Deferred
as a future surface increment, not built now.

## Recommended Approach

**Approach B** — the error-mapping table and the JSON-identical contract
test are the durable parts: the mapping table is the API's real contract
(a single testable unit that stays correct as named errors are added), and
the contract test mechanically enforces "fourth surface, zero new logic"
instead of leaving it as prose. Cost over Approach A is one project
boundary (CC ~2.5h vs ~1.5h).

### Design detail

- New project `src/CsAgent.Http/` referencing `CsAgent.Core`. Exposes a
  `MapCsAgentApi()` extension mapping (Map* convention — endpoint mapping,
  not DI registration; eng-review D5):
  - `POST /ask` `{ "question": string }` → 200 with the canonical
    `AskResult` JSON (both outcomes). Named model-transport failures during
    the ask → 502 ProblemDetails (see taxonomy).
  - `GET /health` → `{"status":"ok"}` 200, no store probe, no model call.
  - **Error-name registry (built as part of step 1):** the named errors
    today are ad-hoc `component/name` strings at the throw sites; the Http
    project enumerates them in one mapping table — `CsAgentException` →
    RFC 9457 ProblemDetails with stable `type` URNs
    (`urn:cs-agent:<component>:<name>`). Status taxonomy:
    malformed request body / missing question → 400; empty store / corrupt
    store / embedding-model mismatch → 503. A named error with no explicit
    mapping → 500 ProblemDetails carrying its component+name (loud
    default, never swallowed). Any NON-named uncaught exception in the
    handler → generic 500 ProblemDetails, no stack, no details — the
    catch-all behind the registry. (A mid-run bad-env 500 is impossible
    after startup fail-fast; the 500 slot exists only as that defensive
    fallback.)
  - **Model-transport failures, mapped to actual Core behavior:** Core has
    NO named transport error. Verify-stage transport failure is CAUGHT by
    `VerifyOnce` and fails closed — it surfaces as an escalate 200 by
    design, unchanged. Caveat (outside voice #2, documented not fixed):
    that escalate's missing-note then reads "verifier output malformed
    twice", misattributing an infra failure as a malformed model output —
    pre-existing Core wording, out of scope this cycle. Draft-stage (and
    retrieval-stage — the query-embedding call inside `retriever.Retrieve`
    is the third model-call site, outside voice #3) transport failure
    propagates as a raw exception; the Http layer maps both by exception
    type — the ONE type-based rule in the registry: an exception that IS
    OR WRAPS (at any `InnerException` depth) an `HttpRequestException` /
    `IOException` → 502 ProblemDetails `urn:cs-agent:model:transport`.
    The wrapper layers (M.E.AI, OpenAI SDK) may re-throw in their own type
    with the transport error nested, so a bare exact-type match would drop
    the 502 signal; the rule's real-world behavior is pinned from a
    dead-BaseUrl live check at implementation (eng-review D4). Any other
    raw exception → the generic 500 catch-all above.
    **Pin result (dead-BaseUrl live check, 2026-09-07):** the OpenAI /
    ClientModel retry path surfaces the failure at the job executor as a
    BARE `System.ClientModel.ClientResultException` with NO inner exception
    (the chain `AggregateException → ClientResultException →
    HttpRequestException → SocketException` seen in direct `pipeline.Run`
    flattens to a single `ClientResultException` through the server path)
    — the rule shipped with `ClientResultException` added to the is-or-wraps
    set; the bare shape has its own scripted test
    (`ClientResultExceptionBare_502ErroredJob`).
  - **Startup fail-fast:** `cs-agent serve` validates env vars at startup,
    then checks `File.Exists` on the resolved store path FIRST — a
    never-ingested corpus refuses WITHOUT constructing the store, because
    construction runs `EnsureSchema` + `SetMeta` and would leave a stray
    empty .db behind after refusing (outside voice #4). Only when the file
    exists: construct the store and check `HasDocuments` — the store
    constructor itself catches corrupt-store and embedding-model mismatch,
    but opening a missing .db silently creates a fresh empty one, so
    construction alone proves nothing about content (eng-review D3). An
    empty store refuses to start: named structured error, non-zero exit.
    Validate loudly applies to the server process, not per request.
    Per-request 5xx is reserved for failures that genuinely surface
    mid-run (transport). The empty-store → 503 mapping below is therefore
    a library-level defense: it is tested by pointing `AddCsAgentApi()` at
    an empty store via `WebApplicationFactory` (bypassing the serve host),
    because through `serve` an empty store never reaches a request.
    Same for the CLI refactor: serializer options live as ONE static
    instance in Core (`CsAgentJson.SerializerOptions`, WriteIndented=true)
    and `ask --json` is refactored onto it, so HTTP response bytes equal
    CLI bytes by construction (eng-review D6).
  - **Concurrency (documented v1 limitation):** `serve` builds ONE ask
    pipeline at startup (after fail-fast) and shares it across requests —
    singleton lifecycle (eng-review D2). `AskPipeline.Run` is fully
    synchronous and the shared store is a single non-thread-safe
    `SqliteConnection` (built once inside `CreateAskPipeline`, never
    re-created per request, so no per-ask connection leak). v1 serializes
    asks behind one `SemaphoreSlim(1)`; concurrent requests queue behind it.
    The handler wraps the pipeline in `Task.Run` so the Kestrel request
    loop is not blocked. One-at-a-time serving is honest for a weekend v1
    with no consumers; the p95 + async upgrade decision revisits it with
    data.
  - Server header suppressed; no stack traces ever reach the body
    (validate-loudly applies: named component + error, message, no trace).
- `cs-agent serve [--port N]` (or `CS_AGENT_PORT` env var; env-vars-only
  rule intact) starts Kestrel hosting the library mapping. **v1 binds
  loopback only** — an explicitly no-auth, no-rate-limit API must not
  default to `0.0.0.0`; non-loopback bind is deferred to the auth work.
- Verdict-before-output holds trivially: the handler awaits the complete
  result before responding.

## Success Criteria

1. `cs-agent serve` starts Kestrel; `curl POST /ask` returns JSON identical
   to `cs-agent ask --json` for the same question on the fake-model seam,
   modulo the nondeterministic `seconds` field (contract test in CI proves
   it; serializer options — including the CLI's indented layout — one
   shared static instance in Core (`CsAgentJson.SerializerOptions`),
   never re-created per surface). Contract test mechanics (outside voice
   #5): compare the HTTP body byte-for-byte against in-process
   `JsonSerializer.Serialize(result, CsAgentJson.SerializerOptions)` —
   byte-identity to `ask --json` holds by construction (same options
   instance, same result object), so no CLI-binary spawn and no
   platform-newline concerns.
2. Escalate is a 200: `resolved:false`, `answer:null`, `missing[]`
   populated — asserted by an explicit test, not assumed.
3. Every named structured error in the registry maps to a ProblemDetails
   `type` URN and the intended status code; malformed body → 400; empty
   store → 503; draft-stage transport → 502 (exception-type rule);
   verify-stage transport → escalate 200 by Core's fail-closed (asserted);
   no stack trace ever in a response body.
4. `GET /health` answers 200 without touching the store or any model.
5. `cs-agent serve` fails fast at startup on a bad env var or missing/mismatched
   store, with a named structured error and non-zero exit.
6. All existing suites (unit, pipeline, eval gates, CI) stay green
   unchanged.
7. p95 latency computed from existing `eval-results/*.json` (one fresh
   live run only if stale), measured BEFORE build (step 0); number
   recorded here and in the TODOS/README as evidence for or against the
   sync-only decision.

**Amended contract (D17/D18/D19) — supersedes the sync /ask shape wherever
Design detail and Next Steps 1-3 conflict:**

- `POST /ask {"question": q}` → **202** `{"id", "status":"running",
  "result":"/result/{id}"}`. Sync /ask is REPLACED — one contract, no mode
  flag (D17).
- `GET /result/{id}` — status carried in body, not in HTTP code; 5xx stays
  reserved for real errors (D19):
  - unknown id → 404
  - running → 200 `{"id","status":"running"}`
  - done → 200 canonical AskResult JSON (escalate included — still a 200
    with `resolved:false` + `missing[]`)
  - job errored at completion → the registry-mapped ProblemDetails status
    and URN (502 transport / 503 store / 500 loud default), recorded on
    the job and replayed to every poll
- Jobs live in-process (`ConcurrentDictionary`, no eviction, no
  persistence — D18): restart loses all ids (poll → 404), resubmit to
  recover. Documented v1 limitation for a loopback single-user tool.
- Job execution serializes behind the same `SemaphoreSlim(1)` — queued
  jobs run one at a time (singleton pipeline unchanged, eng-review D2).
- `CancellationToken` now flows through `AskPipeline.Run` — the ONE
  deliberate Core change, expanding the "zero new logic" premise: retrieve
  / draft / verify calls observe it; server shutdown cancels running
  jobs. VerifyOnce's fail-closed escalate still swallows verify-stage
  failures — unchanged.
- Verdict-before-output holds: a job's result is exposed only after the
  resolve/escalate verdict exists.
- Contract test (SC1) reads: GET /result/{id} body, once done,
  byte-identical to `ask --json` (same `seconds` masking, same in-process
  shared-options mechanics, outside voice #5).
- Everything else from the reviewed plan is unchanged: startup fail-fast
  (File.Exists pre-check → construct → HasDocuments), loopback bind, error
  registry, /health, shared serializer static, server-header suppression.
- Tests added to the reviewed list: 202 submit shape, running→done poll
  transition, 404 unknown id, error-job replay, shutdown cancellation; the
  concurrency serialization test (D7) now guards the job executor.

**Deferred with this increment:** job persistence + eviction/TTL (Docker
era), DELETE /result/{id}, 410 Gone semantics, long-poll.

## Request/error flow (eng review 2026-09-07)

```
POST /ask {"question": q}
   │
   ├─ malformed body / empty question ───────────────→ 400 ProblemDetails
   ├─ SemaphoreSlim(1) wait (serialize, singleton pipeline)
   ├─ Task.Run( AskPipeline.Run(q) ) ── retrieve (embed) ─ draft ─ verify (ONE call)
   │      │
   │      ├─ resolve   ─→ 200 AskResult (resolved:true, answer, citations)
   │      ├─ escalate  ─→ 200 AskResult (resolved:false, answer:null, missing[])
   │      ├─ named CsAgentException ─→ registry: empty/corrupt/mismatch → 503;
   │      │                           unmapped named → 500 (carries component+name)
   │      ├─ wraps HttpRequestException/IOException (draft OR retrieve stage)
   │      │                          ─→ 502 urn:cs-agent:model:transport
   │      └─ any other exception ─→ generic 500 (no stack, no details)
   └─ every response: no stack trace, no Server header

GET /health ─→ 200 {"status":"ok"}   (no store, no model)

serve startup: env validate → File.Exists(store) → construct store →
   HasDocuments → any failure = named structured error + exit 1
   (a bad store never serves a request)
```

## Failure modes (eng review 2026-09-07)

| Codepath | Production failure | Test | Handling | User sees |
|---|---|---|---|---|
| /ask happy path | provider latency spike | serialization test queues behind semaphore | p95 trigger (step 0) | slow-but-complete response (documented) |
| /ask draft transport | provider endpoint down | 502 test (wrapped HttpRequestException) | 502 URN | named 502, retryable |
| /ask verify transport | same outage, verify leg | fail-closed escalate-200 test | escalate + documented caveat | 200 escalate; note may misattribute cause (documented) |
| /ask retrieve transport | embedding endpoint down | same 502 rule (third site, outside voice #3) | 502 URN | named 502 |
| /ask named store error | store corrupted after startup | registry tests | 503/500 URN | named error |
| serve startup | bad env, missing/corrupt/empty store | fail-fast tests | named error + exit 1 | server refuses to start, no stray .db |
| malformed body | client bug | 400 test | 400 ProblemDetails | clear, retryable |

No critical gaps: every failure mode has a test or a documented accepted cost.
