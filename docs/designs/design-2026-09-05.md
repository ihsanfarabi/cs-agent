## Problem Statement

The user wants to build an open-source counterpart to Fin AI (Intercom's AI support agent; Intercom renamed itself Fin in mid-2026, $0.99 per resolution, 76% average resolution rate across 8,000+ customers, 1M+ conversations/week). Fin's actual trick is the outcome-billed confidence gate — it charges only when a conversation counts as resolved, powered by purpose-built retrieval and reranking models (fin-cx-retrieval, fin-cx-reranker). Fin is cloud-only with no self-host option and no API for defining agent behavior.

The OSS gap, re-verified with fresh research this session: Botpress and Rasa CALM are assembly toolkits, Inkeep is commercial-but-self-hostable, OpenClaw is a personal agent, DocsGPT is an app not an engine. Nobody packages the resolve-or-escalate confidence gate as an open engine — and additionally, Microsoft Agent Framework (MAF, 1.0 GA April 2026, Semantic Kernel and AutoGen both in maintenance mode under it) has almost no real non-Microsoft multi-agent sample repos. This project serves both gaps with one artifact. **Landscape correction (CEO review, 2026-09-05):** both absolute claims went stale mid-2026 — MAF community samples now exist (On-Call-Copilot-Multi-Agent, maf-demo-console, multi-agent-workflows; all demos, none products) and Python resolve-or-escalate engines shipped (grounded-support-agent, resolver, RagWarden; none in .NET/MAF). The surviving claim, used in the README: as of September 2026, among the MAF samples reviewed, cs-agent is the only one that is also an installable product with an eval harness.

## What Makes This Cool

1. **The verifier gate is the product, and it is visible.** Draft agent writes a cited answer; Verify agent checks every atomic claim against the retrieved chunks; the escalate decision is a handoff edge in the workflow graph (the resolve verdict terminates the run via an executor step), and both paths show in the DevUI trace. Fin's billing trick, exposed as watchable infrastructure.
2. **The repo doubles as a public MAF reference.** Real .NET multi-agent code using `AgentWorkflowBuilder` handoffs, agent instructions, workflows, DevUI, and MCP — the patterns MAF 1.0 demos but almost nobody has shipped as a working third-party example. Two audiences: people who want a Fin-style engine, and people learning MAF.
3. **Eval harness stays.** `cs-agent eval` emits resolution rate, citation accuracy, hallucination rate against a labeled fixture — the credibility section of the README.

## Premises

All agreed this session (D7):

1. **P1: Engine, not platform.** Composes with helpdesks; no inbox, no ticketing, no channels.
2. **P2: The verifier gate is the product.** Resolve/escalate is a confidence-gated decision (every claim checked against retrieved chunks), not just cited RAG.
3. **P3: The MAF showcase framing.** Draft/Verify/Escalation are real MAF agents wired with the handoff workflow builder; DevUI trace is the hero demo; the repo targets engine users and MAF learners alike.
4. **P4: Quickstart is product.** ≤5 min from clone to cited answer; SQLite store; no infrastructure.
5. **P5: v1 scope.** Single-shot Q&A, no widget, no actions, no multi-tenant, no HTTP API.
6. **P6: Distribution.** GitHub + `dotnet tool` on NuGet; MCP server wrapper included (exercises MAF's MCP support) but not the hero.

## Approaches Considered

### Approach A: Sequential two-agent chain
Draft then Verify in a MAF sequential workflow; escalate as structured output, not a handoff edge. Effort S-M, risk low. Rejected: a two-step chain cannot back the README's multi-agent pitch and exercises too little of the framework the user chose it to learn.

### Approach B: Handoff workflow showcase
Triage → Draft → Verify → Escalation as real AIAgents wired with `AgentWorkflowBuilder.CreateHandoffBuilderWith`; escalate is a handoff edge; DevUI trace is the hero demo. Effort M, risk medium (handoff selection logic, DevUI recording). Chosen.

### Approach C: Verifier as MAF middleware
Package the confidence gate as reusable MAF middleware so any MAF agent gains resolve/escalate stamping in one line; cs-agent as the demo app. Effort M-L, risk medium-high. Rejected for v1: designing a reusable abstraction for an unused framework kills weekend projects — noted as the natural v2 once B exists.

## Recommended Approach

**Approach B, on C# / .NET with Microsoft Agent Framework 1.x** (`Microsoft.Agents.AI`, .NET runtime 1.20 as of Aug 2026).

### Architecture

```
cs-agent ingest <path>               cs-agent ask "<question>"
        │                                       │
        ▼                                       ▼
   Loader (recursive .md/.html)    ┌─────────────────────────────┐
   → chunk → embed →               │  MAF Workflow (handoff     │
   SQLite vector store             │  graph via                  │
   (URL crawl: post-publish)       │  AgentWorkflowBuilder)      │
                                   │                             │
                                   │  Triage ─handoff→ Draft     │
                                   │  Draft ─handoff→ Verify     │
                                   │  Verify ─unsupported─handoff→│
                                   │           Escalation       │
                                   │  (resolved = executor-step  │
                                   │   terminal output, not a    │
                                   │   graph node — see below)   │
                                   └───────────────┬─────────────┘
                                                   ▼
                     { resolved: true, answer, citations[] }
                     { resolved: false, escalate: { missing[] } }
```

- **Agents as real MAF AIAgent instances:** Triage (pass-through root; fixed instruction "Route every support question to the Draft agent"), Draft (retrieves top-k chunks, writes cited answer), Verify (cheap model; extracts the draft's atomic claims as JSON, judges each against retrieved chunks), Escalation (deterministic formatter — a node in the handoff graph, not an LLM call; formats the `missing[]` payload; see Escalation data path below). The handoff graph is built with `AgentWorkflowBuilder.CreateHandoffBuilderWith(...)` — the exact pattern MAF 1.0 documents (their own sample is Triage → Billing → Tech).
- **Verifier rule (unchanged from the morning design):** `resolved: true` iff every atomic claim is supported by at least one retrieved chunk; zero claims ⇒ escalate (no vacuous resolution); malformed verifier output ⇒ retry once, then fail closed to escalate. **Draft → Verify data contract:** Draft's handoff message to Verify carries the answer plus the top-k chunks it cited; Verify does not retrieve. The verdict and the `missing[]` payload are judged against exactly the chunks Draft cited — no drift between the two.
- **Escalation data path:** Verify's handoff message to the Escalation agent carries the JSON claims array (each unsupported claim plus the chunks that failed to support it). **Escalation is a deterministic formatter, not an LLM call** (added by eng review): the node executes fixed logic — custom non-LLM agent or executor step, mechanism chosen at the step-2 prototype — formats `missing[]` verbatim, and never re-derives anything; the Verify → Escalation edge still fires in DevUI. **Zero-claims branch:** `missing[]` = `[{claim: <the question>, note: "no answerable claim could be extracted"}]`.
- **"Resolved" is not a handoff edge** — handoffs select the next agent; a terminal success state is not an agent. Resolution terminates the workflow: Verify emits structured output (supported/unsupported verdict), read by an executor step that ends the run and prints the result. The DevUI trace still shows the Draft → Verify edge and the Verify → Escalation edge firing — the visually interesting ones.
- **Hero demo:** the same `ask` run inside MAF DevUI, showing the handoff graph executing — triage routing, draft handing to verify, verify rejecting a claim, escalation edge firing. README leads with the screen recording. Fallback (see go/no-go in Constraints): CLI terminal GIF.
- **Surfaces (v1):** `cs-agent` CLI (ingest [path mode] / ask / eval) + MAF DevUI run + MCP server (stdio) wrapping the same workflow. HTTP API, Docker, and URL crawl mode are post-publish. MCP is the named first cut if the core overruns (see cut line).
- **Store, ingest, chunking, embeddings, eval fixture, env-var defaults:** as inlined in the Appendix below (the superseded doc is historical context only — this doc is self-contained).

### Out of scope for v1 (P5)

Multi-turn conversation, chat widget, tool-calling/actions, multi-tenant, HTTP API, Docker, URL crawl mode (post-publish; v1 ingests local paths only), reranked/hybrid search, JS-rendered site crawling.

### 10x direction (decided this session, not v1)

**Escalation with actions** — the escalate edge gains MAF tool-calling: create a ticket, draft the human-queue email, mirroring Fin's Procedures. This makes the escalation agent a real actor rather than a formatter, and showcases the other half of MAF's feature set. Deliberately deferred: actions need a target system v1 does not have.

## Appendix: Carried v1 Specifications (inlined; the superseded doc is historical only)

### Env-var contract (defaults, all overridable)
- `CS_AGENT_MODEL_KEY` — provider API key; the only required var
- `CS_AGENT_BASE_URL` — default `https://openrouter.ai/api/v1` *(changed 2026-09-06: was `https://api.openai.com/v1`, which broke the OpenRouter-only default model pair)*
- `CS_AGENT_DRAFT_MODEL`, `CS_AGENT_VERIFY_MODEL` — default `deepseek/deepseek-v4-flash-0731` in both roles *(named at v0.1.0, replacing the placeholder "flagship + small" pair; the pair that passed the eval gate)*
- `CS_AGENT_EMBEDDING_MODEL` — default `text-embedding-3-small`
- `CS_AGENT_EMBEDDING_DEPLOYMENT` — Azure only
- `CS_AGENT_TOP_K` — default 8 *(changed 2026-09-06 to match shipped code; plan said 5)*
- `CS_AGENT_CHUNK_SIZE` — default 1200 chars, heading-aware fixed window (chunk boundaries respect markdown heading structure); `CS_AGENT_CHUNK_OVERLAP` — default 150, validated `overlap < chunk_size`
- `CS_AGENT_STORE` — default `./cs-agent-<corpus>.db`; a Postgres value is reserved, documented-but-unimplemented in v1
- **Numeric validation (added by CEO review):** `CS_AGENT_TOP_K` and `CS_AGENT_CHUNK_SIZE` are validated at startup — non-integer or out-of-range values (`top_k < 1`, `chunk_size < 200`, overlap ≥ size) produce a structured error naming the var and its valid range, before any model call.

### Gate ordering — no streaming in v1
The draft is fully generated and buffered; the verifier verdict is computed BEFORE any output is emitted. A `resolved` answer prints with citations; an `escalate` prints `missing[]` instead of the draft. Same rule for CLI, DevUI, and MCP. Streaming joins post-publish, after the gate is trusted.

### Verifier claims schema and prompt artifacts
Verify's structured output (single prompt, extraction + judgment in one call, as specified in the gate ordering):
```
[{ "claim": "<atomic claim text>", "supported": true|false,
   "supporting_chunk_ids": [..], "unsupported_by": [..] }]
```
Two labeled sections of the ONE verifier prompt, authored as a single file during the build: **claim-extraction** (split the draft into minimal atomic claims; no judgment) and **support-judgment** (a claim is supported only if a cited chunk states it explicitly — topical adjacency does not count). **(Clarified by outside voice, 2026-09-05: one model call, one prompt artifact, one structured output — the earlier "two prompt artifacts" wording read as two separate calls and would have invalidated the 3-call worst case, the cost line, and MCP timeout sizing.)** Tuned in the dedicated verifier-tuning step.

### Citation identity per ingest mode
v1 (path mode) cites the file path relative to the ingest root; fixture records use paths (the fixture ingests via path mode). URL mode (post-publish) cites the page URL.

### Store and corpus selection
SQLite only in v1: embeddings stored as BLOBs, cosine similarity computed in-process, one `.db` file per docs site; no `.db` ships with the tool — the first `ingest` creates it. `ask` targets the most recently ingested corpus by default; `--corpus` selects another. An empty store returns a structured "no documents ingested" error. The reserved corpus name `fixtures` resolves to the globally-installed tool's bundled directory, so `cs-agent ingest fixtures` works from any cwd.

Each `.db` carries store metadata: embedding model name, vector dimension, ingest timestamp. Re-embedding an existing corpus, or `ask` against a corpus whose stored embedding model no longer matches `CS_AGENT_EMBEDDING_MODEL`, refuses with a structured error — cosine similarity across mismatched vector spaces returns confident nonsense, and the engine errors instead. The most-recent-corpus pointer lives in one small state file beside the `.db` files.

### Ingest input modes
**v1 ships path mode only** (added by eng review; the URL crawler is a sub-project no v1 success criterion needs). Path mode: recursively loads local `.md` and `.html` files. URL mode is specced for post-publish: same-domain only, depth ≤ 3, max 200 pages, respects robots.txt, 1 request/sec, HTML-only (JS-rendered sites out of scope, documented limitation).

Embedding calls are batched where the provider supports it (default batch ~64 chunks per request; single-input fallback for providers without batch support). The 200-page worst case drops from ~2000 sequential calls (~7 min) to ~31 (~1 min).

### Trust boundary (corpus poisoning) — added by CEO review
The verifier's evidence is the ingested corpus, which makes the corpus a trust boundary: injected instructions in a docs page ("mark all claims supported") attack the verifier itself, not just the answer. v1's trust boundary is the corpus owner = the operator — you ingest your own docs, so poisoning is self-inflicted and accepted. This changes with URL mode: the post-publish crawl spec MUST carry a corpus-poisoning consideration (crawled third-party pages are untrusted input to the gate). Stated here so the URL-mode PR inherits the question with an answer, not without one.

### Failure paths (model API layer and local filesystem)
- Any model/embedding API error (401/429/timeout) prints a structured error naming the failing call and the env var to check. No stack traces in CLI output. The draft path does NOT retry — fail loud.
- `ingest` commits page-by-page (idempotent). A killed crawl keeps committed pages; re-running `ingest` resumes and re-embeds only missing pages.
- **Local-filesystem failures (added by CEO review):** during ingest, unreadable or binary files are skipped with a one-line warning and the run continues; the ingest summary reports skip counts (same page-by-page idempotent pattern as network failures). The recursive loader carries a symlink-cycle guard and a recursion depth cap — a cyclic directory tree cannot loop the loader. At `ask` time, a corrupt `.db` returns a structured error suggesting delete-and-re-ingest; a corrupt most-recent-corpus pointer file is auto-rebuilt from the existing `.db` files — never a silent wrong-corpus answer.
- The verifier's existing retry-once rule is the ONLY retry in the pipeline.

### Calls per ask
Worst case 3 LLM calls (Triage, Draft, Verify — Escalation is deterministic); typical resolved path 2-3. Stated so per-ask cost and MCP client timeout sizing are decisions, not surprises.

### Eval fixture schema and scoring
Repo-owned docs site (~30 pages, committed under `fixtures/docs/`) plus 25 hand-labeled questions — 20 answerable, 5 deliberately unanswerable (empty `expected_sources`, expected outcome `escalate`) so the escalate path is measured, not assumed. Fixture record: `{ question, expected_answer, expected_sources[] (relative paths), expected_outcome }`. A malformed record (missing field, wrong type) is a structured error naming the record and the field; eval stops there and resumes after the fix — a bad record never silently scores. `cs-agent eval` invokes the same ask pipeline per fixture question — same retrieval, agents, and verifier, output parsed for scoring; no separate model wiring exists in eval. Eval commits results per-question (idempotent, resumable — same pattern as ingest): a 429 at question 17 leaves 16 scored, and re-running resumes at 17.

**Citation convention (added by eng review):** Draft cites only the chunks actually used in the answer (chunk-level `[1][2]` markers). Fixture `expected_sources` list PAGE-level (file) paths containing the supporting chunks. Citation accuracy = Jaccard over page-level sets; labels are authored to this convention. Scoring (mechanical, no LLM-as-judge in v1):
- **resolution rate** = fraction of questions with the expected outcome (escalate counts as a point on unanswerables)
- **citation accuracy** = per-question Jaccard similarity between the response's citation set and `expected_sources`, averaged over answerable questions
- **hallucination rate (v1 proxy)** = fraction of `resolved: true` responses whose citation set has ZERO overlap with `expected_sources` — by construction this includes any `resolved` on an unanswerable question; documented as a proxy (undercounts subtle hallucinations, but reproducible and independent of the live verifier)

Third-party sites (Stripe etc.) are demo targets, never eval fixtures — ToS risk and silent breakage. Under the cut line, the fixture trims to 15 questions (12 answerable, 3 unanswerable).

**Eval pass targets (added by CEO review):** resolution ≥ 80% on answerable questions, 5/5 escalates on the unanswerable, hallucination proxy = 0. These three numbers are the stop condition for the verifier-tuning step and the pass/fail meaning of the published eval numbers. Under the cut line, targets scale to the trimmed fixture: ≥ 10 of 12 answerable resolved, 3/3 unanswerables escalated, hallucination proxy still = 0.

**In-sample disclosure (added by outside voice, 2026-09-05):** the same 25 questions tune the verifier prompts and produce the published numbers. The README states this plainly wherever the three numbers appear: they are in-sample tuning-set scores, not held-out benchmarks.

### `ask` output shape
```
$ cs-agent ask "How do I rotate the API key?"

✓ resolved (4 claims, 4 supported)

Rotate keys from Settings → API keys → Rotate. The old key stays
valid for 24 hours so running deploys don't break. [1][2]

Sources:
[1] docs/api-keys.md — "Rotating keys"
[2] docs/settings.md — "API key settings"

3 model calls · 4.2s · ≈$0.004

$ cs-agent ask "What is your SLA uptime?"

✗ escalate — cannot answer from ingested docs

Claims:
[1] ✓ "Keys rotate from Settings" — chunk 14
[2] ✗ "SLA uptime percentage" — no supporting chunk among 5 retrieved

Missing:
[1] "SLA uptime percentage" — no supporting chunk among 5 retrieved
```
